# Tasks: Invoice History

**Input**: Design documents from `/specs/010-invoice-history/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/invoice-history-api.md, quickstart.md

**Tests**: Included. FR-016 requires automated tests, and the acceptance checks in contracts/invoice-history-api.md map to test tasks below.
Write each phase's tests first and confirm they fail (a test that does not compile yet counts as failing).

**Organization**: Grouped by user story (US1 every change is recorded, US2 read an invoice's history, US3 history cannot be changed). The
history entity, the current-user port and its adapter, the store's history members and their fakes, the `InvoiceService` constructor change, the
table with its trigger (one migration) and the EF store are Foundational because all three stories need them. **US1** builds the pure builder
and makes the five write paths of `InvoiceService` record their entry in the same save; **US2** adds the read (service, route, screen, link);
**US3** proves that nothing can change or remove an entry (the trigger is created by the Foundational migration; US3 proves it, and the
application's lack of any write route, method or control, and that later events never touch earlier entries).

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies on incomplete tasks)
- **[Story]**: US1, US2, US3 (setup, foundational and polish tasks carry no story label)

## Path Conventions

`backend/src/BillingCrm.*`, `backend/tests/`, `frontend/src/app/` as in plan.md. All commands run from the repository root unless a task says
otherwise (`cd /c/Users/somam/source/repos/billing-crm` first in Bash: the shell's directory drifts); run frontend commands from `frontend/`
(`npx --yes npm@11 exec -- ng test --watch=false`). Run the three backend test projects **one at a time**. Stop the API and `ng serve` before
`dotnet build`, `dotnet test` or `dotnet ef`; **do not start them again unless the developer asks**. Edit code files with the Edit and Write tools
(shell string replacement and long heredocs have mangled code and quotes before).

**Rules that apply to every task**: use the `minimal-api-conventions`, `angular-ui-conventions`, `sql-migrations` and `invoice-money` skills for
matching edits; **an entry is recorded only after every check has passed and immediately before the one save, and is written by that same save**
(a refused change, a validation error, a save that changes nothing and a lost race write no entry); **nothing anywhere updates or deletes an entry**
(no store method, service method, route or control; `InvoiceHistoryEntry` has no setters and no mutating methods); **the user is the signed-in
user's email and role from `ICurrentUser` and never a request field**; every value in an entry is **text as it was at the time** (money as exact
invariant two-decimal text) and is never recalculated or re-read from a customer, product or user; expected failures are `Result` -> `ProblemDetails`
(only a missing signed-in user inside `ICurrentUser` throws: a defect); money is `decimal`, never `float`/`double`; the status shown in an entry
is the stored status (never `Overdue`); every endpoint declares its access explicitly; the Angular screen shows the values exactly as received and
calculates nothing, and has no control that could change history; the aggregate `Invoice` does **not** own or load history; no connection string,
key or credential in any committed file; Arabic and English text must round-trip unchanged; no entries for other events, no history for customers,
products or staff, no cross-invoice list, search, export, undo, comments, purge or backfill (FR-017); do not change customer or product behaviour.

  example (send an invoice, open History, see your Sent row). US3 then proves the immutability that the migration's trigger and the lack of any
  write path already give.
