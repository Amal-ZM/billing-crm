# Data Model: Customers

**Feature**: 003-customers | **Date**: 2026-09-24

## Entity: Customer (table `Customers`)

| Column | Type | Rules |
|--------|------|-------|
| `Id` | `uniqueidentifier` | Primary key, generated by the application |
| `Name` | `nvarchar(200)` | Required. Trimmed. Any script (Arabic, Latin, mixed) |
| `Type` | `nvarchar(20)` | Required. Exactly `Company` or `Individual`, enforced by the domain enum and check constraint `CK_Customers_Type` |
| `Email` | `nvarchar(256)` | Required. Trimmed, casing kept as entered |
| `NormalizedEmail` | `nvarchar(256)` | Required. Trim + upper-invariant. **Unique index** `IX_Customers_NormalizedEmail` |
| `Phone` | `nvarchar(20)` | Required. Trimmed. 7-20 characters: digits, spaces, `+`, `-`, `(`, `)` |
| `VatNumber` | `nvarchar(30)` null | Optional. Trimmed; empty becomes `NULL`. Letters, digits, spaces, hyphens |
| `Address` | `nvarchar(500)` | Required. Trimmed. May contain line breaks |
| `IsActive` | `bit` | Required. `true` when created |
| `CreatedAtUtc` | `datetime2` | Required. Set once, from `TimeProvider` |
| `UpdatedAtUtc` | `datetime2` | Required. Equals `CreatedAtUtc` on creation; updated on any real change |

- Indexes: `IX_Customers_NormalizedEmail` (unique), `IX_Customers_Name` (list sort order).
- Uniqueness covers **all** customers, active and inactive: an inactive customer keeps its email.
- No money columns (nothing here uses `decimal(18,2)`).
- No foreign keys yet; invoices (later spec) will reference `Customers.Id`.

## State: active / inactive

```text
Created --> Active  <----->  Inactive
```

- Any signed-in staff member may toggle in either direction, any number of times.
- Inactive customers remain in the list and in search results, keep every field and their reserved
  email. Setting the value it already has changes nothing (including `UpdatedAtUtc`).
- The invoice spec will read `IsActive` to refuse new invoices for inactive customers; this spec does
  not enforce that.

## Domain types

- `CustomerType` (Domain enum): `Company`, `Individual`.
- `Customer` (Domain entity): fields above; `Create(...)`, `Update(...)`, `SetActive(...)` methods
  that set the timestamps passed in by the service. `NormalizeEmail` reuses `StaffUser.NormalizeEmail`'s
  rule (moved to a shared Domain helper so both use one implementation).

## Application types

- `CustomerDto` (all fields plus timestamps), `CustomerListItem` (id, name, type, email, phone,
  vatNumber, isActive), `CustomerInput` (name, type, email, phone, vatNumber, address; one type used
  for both add and edit, every value a nullable string as it arrives in JSON), `SetActiveRequest(bool?
  IsActive)`, `CustomerQuery(Q, Type, Active, Page, PageSize)` (all **strings**, exactly as they arrive
  in the query string, so a bad value becomes a named field error) which the service parses into the
  validated `CustomerSearch(Text, Type, IsActive, Page, PageSize)`, and
  `PagedResult<T>(items, page, pageSize, totalCount, totalPages)` (total pages by integer arithmetic).

## Migration

- `AddCustomers` (Infrastructure). Applied with `dotnet ef database update`. Never edited after it
  has been applied; later changes get new migrations.
