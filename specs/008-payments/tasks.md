**Input**: Design documents from `/specs/008-payments/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/payments-api.md, quickstart.md

**Tests**: Included. FR-015 requires automated tests, and the acceptance checks in contracts/payments-api.md map to test tasks below.
Write each phase's tests first and confirm they fail (a test that does not compile yet counts as failing).

**Organization**: Grouped by user story (US1 record payments and settle an invoice, US2 refuse the payments that must not be recorded
and the cancel rule, US3 see what has been paid). The entity, the aggregate rules, the validator, the migration, the store change, the
response additions and the client models are Foundational because all three stories need them. Recording and refusing are one code
path (research R8): **US1 builds the service method and the route with all the rules**; **US2 proves every refusal at every layer,
adds the cancel rule, and builds the form's refusal handling**; **US3 adds the paid and remaining figures, the payments list and the
Paid badge to the screens**.

## Path Conventions

`backend/src/BillingCrm.*`, `backend/tests/`, `frontend/src/app/` as in plan.md. All commands run from the repository root unless a task
says otherwise (`cd /c/Users/somam/source/repos/billing-crm` first in Bash: the shell's directory drifts); run frontend commands
from `frontend/` (`npx --yes npm@11 exec -- ng test --watch=false`). Run the three backend test projects **one at a time**. Stop the
API and `ng serve` before `dotnet build`, `dotnet test` or `dotnet ef`; **do not start them again unless the developer asks**. Edit code
files with the Edit and Write tools (shell string replacement has mangled backticks and quotes before).

**Rules that apply to every task**: use the `minimal-api-conventions`, `angular-ui-conventions`, `sql-migrations` and `invoice-money`
skills for matching edits; expected failures (not found, wrong status, has payments, overpayment, invalid field, lost race) are
`Result` -> `ProblemDetails`, never exceptions (only a payment reaching an invoice that is not Sent, or one above the remaining,
throws in the aggregate, and the service refuses first); the invoice's **status is judged before the payment's contents**; the legal
changes are the four in `InvoiceStatusRules`, and **Sent to Paid is never offered to a person** (`allowedTransitions` never lists it,
no route sets it); **paid and remaining are calculated only on the server** from the frozen grand total by `InvoiceMoney.Balance`
and never stored; money is `decimal` (`decimal(18,2)`), never `float`/`double`, and a value with a third decimal place is refused,
never rounded; **payments are never edited, voided or deleted** (no `PUT`, `PATCH` or `DELETE`, no such screen); an invoice with
payments cannot be cancelled; the Angular code never re-derives a rule or calculates money (it uses `acceptsPayment`,
`allowedTransitions`, `paid`, `remaining`); no connection string, key or credential in any committed file; every endpoint declares its
access explicitly; do not change customer or product behaviour; Arabic and English text (notes) must round-trip unchanged; this is a
**record of money received, not a payment gateway** (no card, no charging, no refunds, no receipts).
